# 外部架构评审的逐条评价与采纳决策(2026-10-08)

背景:把当时的记忆/缓存架构文档发给 GPT 评审,收到长文反馈。本文是我们对其结论的判断与决策。
原文要点不复述,只记录我们的判定。**结论先行:认同 80%,采纳其 P0 全部、P1 部分;拒绝其基础设施类建议(FTS5/图数据库/公式化检索)。**

## 一、认同并采纳

### 1. P0:取消逐轮滑动截断,让压缩成为唯一的历史重塑机制 ✅ 已实施
- 评审指出的矛盾是真的:16 轮硬截断先于 72k 压缩生效,压缩从未运行;每次截断整段前缀缓存 miss(实测小蜜命中率一度从 96% 掉到 44%,就是截断瞬间)。
- 决策:`MaxHistoryTurns` 16→40→本次进一步放大为"仅极端兜底"(80),`CompressHistoryAsync` 是唯一的结构化压缩(checkpoint 语义:一次性换代,不是每轮滑动删)。

### 2. P0:高频 Progress、动态 People 检索移到观察尾部 ✅ 本次实施
- 与我们此前独立分析的结论一致(见 memory-cache-architecture.md 的"倒数第二阻断效应"一节)。
- 决策:`messages[1]` 只保留低频稳定层(里程碑/反思/旧事件/长期近况);每轮观察尾部携带:服务器事实快照(等级/金币/主手/在干嘛)+ 当前视野内玩家的印象检索(按需、短小)。
- Progress 从"每10分钟写长期记忆"改为"每轮观察实时生成,不落长期记忆"(升级仍记里程碑)。

### 3. P0:Thinking+tools 的 reasoning_content 兼容性 ⚠️ 记录前提,不改
- 评审说 DeepSeek 带 tools 时历史须传回 reasoning_content,否则可能 400 —— 这是针对**标准 multi-turn function calling**(历史含 role=tool/tool_calls 结构)的要求。
- 我们的 assistant 历史消息是自定义摘要文本(思考+动作),**不含 tool_calls 结构**,DeepSeek 按普通对话历史处理 —— 这是对协议的有意简化,规避了该要求,已稳定运行数百轮。
- 风险记录:若未来改为标准 tool calling 协议(传回 tool_calls+tool 回执),必须同时处理 reasoning_content 传回。见 roadmap。

### 4. P1:Goal / Commitment 系统 ✅ 列为下一步最高优先级
- 评审最有价值的观点:"Bot 记住'明晚8点组队'只是记忆;到点主动准备药水、邀请组队,才是有持续性的行为"。这与"活人感"目标直接挂钩。
- 决策:设计 `{Goal | Commitment | Plan | PendingTask}`,带时间/条件触发,到期唤醒思考。数值关系(trust/familiarity/affinity)一并设计但实现从简。

### 5. P1:事实权威分层(服务器事实 vs 主观信念)✅ 渐进采纳
- "谁有权决定真假":等级/金币/交易完成与否是服务器事实;印象/推测是主观信念,应带置信度和证据,不可覆盖服务器事实。
- 渐进路线:People 从"单条文本"升级为"印象追加列表(不互相覆盖)+ 未了事项(unresolved)";数值关系与 evidenceIds 后置。服务器自动事件(Episodes)与 LLM 记忆事件标 source 字段。

### 6. P2:Reflection 改事件驱动 ✅ 采纳
- "打怪100次不需要反思;第一次被朋友背叛值得立即反思"。当前 20分钟+5条的机械触发已产生废话反思("羊不掉好东西")。
- 决策:触发条件改为 importance≥4 的事件尽快反思;低重要度攒批;会话结束(下线)批量整理。

## 二、不认同 / 拒绝

### 1. SQLite FTS5 / 倒排索引 / 图数据库 —— 拒绝
4 个 bot,Episodes 上限 200 条,内存 for 循环打分绰绰有余。引入外部存储换不来可感知收益,还增加运维面。等 bot 数量或事件量上两个数量级再议。

### 2. 检索公式 S=4I+3E+2P+2R+3O-2D —— 拒绝公式本身,采纳方向
权重是拍的,没有验证手段就会变成玄学调参。采纳其中三个方向:意图相关(当前在干什么→相关记忆优先)、去重(同类事件只留最近)、承诺优先(未完成 Goal/Commitment 相关记忆加权)。

### 3. "94-96% 命中率与滑动截断矛盾,需交叉验证" —— 现象已解释
不矛盾:截断只发生在到达阈值的一瞬(实测掉到 44% 后迅速回升),稳态命中率是截断间隙的测量。评审的怀疑精神正确,但结论已被日志数据闭环。

### 4. user_id 隔离导致跨 bot 缓存失效 —— 前提不成立
我们从未传 user_id,四个 bot 同一缓存域,公共头互相命中(冷启动后第二个 bot 首跳 72% 命中即为实证)。评审的警告在"设置了 user_id"时才成立。记录前提:若未来按隐私需要设置 user_id,须重新测量跨 bot 命中。

### 5. 压缩阈值 24k-32k —— 部分采纳
"不越早压缩越好"认同。但我们单轮观察 ~500 token,24k 意味着 ~50 轮历史,对话连贯性会被过早压缩损害。维持 72k,把滑动截断让位(见一.1)。

## 三、评审没提但我们要记的

1. **跨 bot 首跳命中靠公共头字节级一致** —— 任何"个性化 system 前缀"的改动都会破坏它,改 CommonPromptHead 时四个号必须同步。
2. **观察消息里的字段顺序即缓存单元边界的一部分** —— 字段增删要慎重,尽量追加在尾部。
3. **工具定义是静态 JArray** —— 已满足"不要每轮动态修改 tools";将来加工具=所有 bot 的 system 变化+缓存换代,选低峰期做。
4. 成本侧真正的变量是 completion/thinking token 和调用频率,不只是缓存命中率 —— [Bot缓存] 日志已记录 hit/miss,后续补 completion_tokens 统计。
